## 检测 B

### B-1 为什么 Create 有默认值、Update 没有？

> 新建时给默认值 `False` 是安全的——它是**无中生有**：客户端不给就是"未完成"，**不覆盖任何已有数据**，所以允许省略。
> 替换时必须必填，否则省略 `done` 会用默认值**覆盖掉已有的值**（把已完成改回未完成），属于**静默的数据破坏**。
>
> **一句话：新建的默认值不丢数据，替换的默认值会丢数据。**

### B-2 `todo.title` 和 `t["title"]` 为什么不一样？

> `todo` 是 **Pydantic 类的实例** → **属性访问**（点号），像 C++ 的 `obj.field`。
> `t` 是**字典** → **按键取值**（方括号）。注意是**按键，不是按下标**——`todos[0]` 才是按下标。
> 写错会直接抛 `AttributeError` 或 `TypeError: 'X' object is not subscriptable`。

### B-3 `status_code=201` 是给谁看的？

> 给**调用方的程序**看。客户端靠它做分支判断（201/422/404 走不同逻辑），**而不是解析 body 去猜结果**。
> 因为 body 结构不统一（你自己的 404 `detail` 是字符串、框架的 422 `detail` 是数组），有时甚至没有 body（204）——**只有状态码是标准化的分类。**

### B-4 `default=0` 干什么用的？

> `max` 必须返回一个值；序列为空时没有任何值可返回，会抛 `ValueError`。
> `default=0` = "空的时候返回 0"。
> 所以空列表时 `0 + 1 = 1`，第一条任务的 id 是 **1**。

### B-5 删掉 `default=0` 会怎样？

> 空列表时抛 `ValueError: max() arg is an empty sequence`，FastAPI 返回 **500**。
> 只在"把任务全删光"之后才触发——典型的**边界条件**，平时测不出来。

## 检测 C

### C-1 删光后新增，id 是几？有什么问题？

> 是 **1**。问题是 **id 被复用了**：id 1 之前属于另一条已经删除的任务。
>
> 危害：
> - 分享出去的链接 `/todos/1` 指向了**完全不同的东西**
> - 日志无法追溯（"删除 id 1"和"修改 id 1"可能是两个不同的对象）
> - 以后加关联表（评论等）会**挂错对象**
>
> 根因：id 由"当前数据的最大值"算出，**依赖数据状态**。
> 解法：数据库的 `AUTOINCREMENT` 用一个**只增不减的计数器**，保证 id 永不复用。

### C-2 为什么不共用一个模型？

> 因为它们是**不同操作的输入契约**，而不是"资源本身的结构"。
> 共用 `TodoCreate` → PUT 会静默覆盖 `done`；共用 `TodoUpdate` → POST 被迫多写一个字段。
> 真实项目里通常有一组：
> `TodoCreate`（创建能传什么）/ `TodoUpdate`（整体替换必须传什么）/ `TodoPatch`（局部更新）/ `TodoRead`（返回给客户端什么，含 id 等客户端不能决定的字段）。

### C-3 只改标题、不动 `done`，PUT 能做到吗？

> **做不到。** PUT 是整体替换，必须把 `done` 一起传 → 得先 GET 再 PUT。
> 而且并发下会**丢失更新**：别人在你 GET 和 PUT 之间改的值，会被你用旧值覆盖掉。
> 正确做法是 **`PATCH`**：**只改请求里出现的字段，其他一律不动**（`if patch.title is not None:`）。
