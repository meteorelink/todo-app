## 一、先破除神秘感：数据库到底是什么

**一句话：一个「能被程序高效读写的、结构化的文件」。**

### 和 `todos = [...]` 对比

| | `todos = [...]` | 数据库 |
|---|---|---|
| 存在哪 | **内存**，进程一停就没 | **磁盘文件**，永久 |
| 谁能访问 | 只有这个进程 | **任何程序**都能连 |
| 找一条记录 | 自己写 `for` 循环遍历 | 一条 `SELECT` 语句 |
| 并发 | 多线程会串数据 | 数据库自己处理 |

### 那为什么不能自己写个文件（JSON/txt）？

因为要自己解决的问题太多：

| 问题 | 你得自己实现 |
|---|---|
| 查得快 | 索引结构（B+ 树） |
| 断电不坏 | 日志、原子写、崩溃恢复 |
| 多人同时写 | 锁、事务 |
| 数据合法 | 约束（不能为空、必须唯一） |

**数据库把上面四项全包了。这就是它的全部价值。**

### 表 / 行 / 列

```
todos 表
┌──────┬──────────────────┬──────┐
│  id  │      title       │ done │   ← 列（字段 / column）
├──────┼──────────────────┼──────┤
│   1  │  写实验报告       │   0  │   ← 行（记录 / row）
│   2  │  复习数据结构     │   1  │
│   3  │  跑步 30 分钟     │   0  │
└──────┴──────────────────┴──────┘
   ↑
 主键（primary key）：每行的唯一身份证
```

| 数据库概念 | 你已经会的对应物 |
|---|---|
| 表 | **结构体数组** `Todo todos[3]` |
| 列 | 结构体的**字段** |
| 行 | **数组的一个元素** |
| 主键 | 元素的**唯一标识**（不是下标） |
| 建表 | `typedef struct { ... } Todo;` |

**它不是新东西，是你熟悉的东西加上「持久化 + 高效查询」。**

## 二、SQL 的本质：声明式语言

**这是学 SQL 最反直觉的一点，也是最重要的一点。**

| | 命令式（C / Python） | **声明式（SQL）** |
|---|---|---|
| 你写什么 | **怎么做**（循环、比较、赋值） | **要什么**（结果的描述） |
| 例子 | `for t in todos: if t["id"]==id: ...` | `SELECT * FROM todos WHERE id = ?` |
| 谁决定执行方式 | **你自己** | **数据库自己** |

### 你从来不说"怎么找"

```sql
SELECT * FROM todos WHERE done = 0
```

你**没说**：从头遍历？用索引？建哈希表？多线程？

**数据库自己决定。** 它可能建索引、可能并行扫描、可能用缓存——**你完全不参与**。

> **类比 C 语言**：
> 写快排时，每一步比较和交换都得自己写。
> 但用 `qsort()` 时，你只提供一个比较函数，**"怎么排"是库的事**。
>
> **SQL 把"怎么执行"交出去交得更彻底——彻底到连"我用不用索引"都不告诉你。**

### 一个直接推论

**标准 SQL 里没有循环、没有 `if`、没有函数定义。**

你只描述"结果长什么样"，不描述"怎么算出来"。

所以 **SQL 写得好不好，取决于你会不会描述需求**，而不是会不会写算法。

## 三、五条语句（全部围绕你的 todos 表）

> ⚠️ 三条语法速记：
> - **关键字大小写不敏感**，但惯例**大写**（`SELECT` 而不是 `select`）
> - **字符串用单引号** `'abc'`
> - **每条语句以分号 `;` 结尾**

### ① CREATE TABLE —— 建表（定义结构）

```sql
CREATE TABLE todos (
    id    INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT    NOT NULL,
    done  INTEGER NOT NULL DEFAULT 0
);
```

| 写法 | 含义 |
|---|---|
| `CREATE TABLE todos (...)` | 建一张叫 `todos` 的表 |
| `id INTEGER PRIMARY KEY AUTOINCREMENT` | 整数、**主键**、**自增**（见第七节） |
| `title TEXT NOT NULL` | 文本，**不允许为空** |
| `done INTEGER NOT NULL DEFAULT 0` | 整数，不允许为空，**默认 0** |

#### ⭐ 注意 `NOT NULL` —— 这是第二层防线

```
HTTP 请求（无类型的 JSON）
      │
      ▼  第一层：Pydantic 校验
   你的 Python 代码
      │
      ▼  第二层：数据库约束（NOT NULL / 类型）
   数据库
```

**同一个校验，在两个边界上各做一次。**

**为什么要重复？** 因为**不是所有数据都从你的 API 进来**：

- 你以后写脚本批量导入数据
- 你手动用数据库工具改了几行
- 以后有别的服务共用这个库

**Pydantic 只保护 API 这一条路；`NOT NULL` 保护整个库。** 这叫**纵深防御**（defense in depth）。

#### ⚠️ SQLite 没有布尔类型

`done` 只能是 `INTEGER`，用 **`0`/`1`** 表示 `false`/`true`。

这就是"类型转换"问题的来源：**API 层是 `true`/`false`，数据库层是 `1`/`0`，中间必须显式转换。**

### ② INSERT —— 增（对应 POST）

```sql
INSERT INTO todos (title, done) VALUES ('写实验报告', 0);
```

| 部分 | 说明 |
|---|---|
| `INSERT INTO todos` | 往哪张表插 |
| `(title, done)` | **要提供哪些列** |
| `VALUES ('写实验报告', 0)` | 对应的值，**顺序要一一对应** |

**注意：你没有提供 `id`** —— `AUTOINCREMENT` 会自己生成。

> ⚠️ **字符串必须用单引号**。这是 SQL 标准。又一次引号陷阱。

INSERT 之后要拿新 id（Python）：

```python
cursor.execute("INSERT INTO todos (title, done) VALUES (?, ?)", (title, done))
new_id = cursor.lastrowid      # ← 数据库刚分配的 id
```

**`lastrowid` 就是你以前手算的 `new_id`。差别是：这个 id 永不复用。**

### ③ SELECT —— 查（对应 GET）

```sql
-- 全部
SELECT * FROM todos;

-- 只要某些列
SELECT id, title FROM todos;

-- 只看未完成的
SELECT * FROM todos WHERE done = 0;

-- 只看某一条
SELECT * FROM todos WHERE id = 3;

-- 排序（倒序）
SELECT * FROM todos ORDER BY id DESC;
```

| 部分 | 含义 |
|---|---|
| `SELECT *` | `*` = 所有列（也可写列名） |
| `FROM todos` | 从哪张表 |
| `WHERE done = 0` | **过滤条件** |
| `ORDER BY id DESC` | 按 id **倒序**（`DESC` 降序 / `ASC` 升序） |

**⭐ `SELECT` 是只读的** —— 它不修改任何数据。这对应 HTTP 里 `GET` 是"安全方法"的语义：安全的操作可以被缓存、被爬虫反复调用、被浏览器预取。

**REST 设计和 SQL 在这里是同一套思想。**

### ④ UPDATE —— 改（对应 PUT）

```sql
UPDATE todos SET done = 1 WHERE id = 3;
```

| 部分 | 含义 |
|---|---|
| `UPDATE todos` | 改哪张表 |
| `SET done = 1` | 把哪个列改成什么值（多个用逗号） |
| `WHERE id = 3` | **改哪些行** |

#### 🔴🔴 头号警告：永远别忘了 `WHERE`

```sql
UPDATE todos SET done = 1;        -- ❌ 把【整张表】所有行都改了！
```

**这不是"可能会发生"，这是"每个 SQL 使用者都干过至少一次"的事故**，而且**不可撤销**。

**养成习惯：写 `UPDATE` 和 `DELETE` 时，先写 `WHERE`，再回头写前面。**

### ⑤ DELETE —— 删（对应 DELETE）

```sql
DELETE FROM todos WHERE id = 3;
```

#### 🔴🔴 同样的警告

```sql
DELETE FROM todos;                -- ❌ 清空整张表！
```

> **`DELETE FROM todos`** 只删数据、留着表结构。
> **`DROP TABLE todos`** 连表一起删 —— **那个更狠。**
> 记住这两个词的区别，别在真实数据库上试。

| # | 事故 | 后果 | 防法 |
|---|---|---|---|
| 1 | **忘写 `WHERE`** | 全表被改/被删 | 先写 WHERE 再写前面 |
| 2 | **用字符串拼 SQL** | **被注入，数据泄露或全毁** | **参数化查询** |
| 3 | **忘 `commit()`** | 改了没生效，白忙 | 改完就 commit |

## 五、⭐ SQL 注入：为什么参数化能防住

### 危险的写法

```python
# ❌ 绝对不要这样写
sql = f"SELECT * FROM todos WHERE id = {id}"
cursor.execute(sql)
```

**如果用户传来的 `id` 不是数字，而是一段 SQL**，它就被**拼进了 SQL 语句本身**：

```sql
-- 用户输入：1 OR 1=1
SELECT * FROM todos WHERE id = 1 OR 1=1        -- 条件永远为真 → 返回全部数据

-- 用户输入：1; DROP TABLE todos; --
SELECT * FROM todos WHERE id = 1; DROP TABLE todos; --   -- 表没了
```

### 安全的写法

```python
# ✅ 正确
cursor.execute("SELECT * FROM todos WHERE id = ?", (id,))
```

**改动很小：把 `?` 当占位符，把值单独作为第二个参数传进去。**

### ⭐ 为什么这样就安全了 —— 核心认知

**因为 SQL 语句的「结构」和「数据」走了两条不同的路。**

| | 字符串拼接 | 参数化查询 |
|---|---|---|
| 传过去的东西 | **一整根字符串**（结构+数据混在一起） | **SQL 模板** + **数据**，分开传 |
| 数据库怎么处理 | 只能把这根字符串**整体当代码解析** | **先把模板解析成结构并锁定**，再把数据**填进占位符** |
| 数据的身份 | **可能被当成代码** | **永远是数据** |

**关键在时序**：参数化时，**SQL 的结构在数据到达之前就已经解析并固定了**。数据后到，只能乖乖当数据，**它已经没有机会改变语句结构了**。

### 🔗 你其实在 C 里见过一模一样的东西

**格式化字符串漏洞（format string vulnerability）：**

```c
printf(user_input);          // ❌ 用户输入里的 %s %n 会被当成格式说明符！
printf("%s", user_input);    // ✅ 数据永远当数据
```

| | C | SQL |
|---|---|---|
| 危险 | `printf(user_input)` | `f"... {user_input}"` |
| 安全 | `printf("%s", user_input)` | `execute("... ?", (user_input,))` |
| 根因 | **代码和数据结构混在一根字符串里** | **同左** |
| 解法 | **模板和数据分开传** | **同左** |

**完全同构。** 操作系统 / 安全课上学过的东西，在这里换个场景又出现了。

> ⭐ **抽象版本（值得记住）：**
> **只要「数据」有机会被当成「代码」解析，就有漏洞。**
> 这个模式在 SQL、Shell、C 的 `printf`、模板引擎、反序列化里会反复出现。

## 六、`commit()` 与事务

### 为什么改了要 commit？

```python
cursor.execute("INSERT INTO todos (title, done) VALUES (?, ?)", ("买牛奶", 0))
conn.commit()      # ← 少这一行，数据不会真的写进数据库！
```

**类比 C 语言**：

```c
fwrite(buf, 1, n, fp);
fflush(fp);        // ← 类似 commit
fclose(fp);        // ← 类似关闭连接
```

**写进缓冲区 ≠ 落到磁盘。** `commit()` 就是"确认落盘"的动作。

> ⚠️ **初学者最常见的 bug 之一**：代码逻辑全对，接口返回 200，但数据就是没进去——**因为忘了 `commit()`**。
> 而它**不报错**。又是"静默失败"那一类。

### 什么是事务（transaction）？

> **一组操作，「要么全部成功，要么全部失败」。**

**经典例子：转账**

```
A 账户 -100
B 账户 +100
```

如果执行完第一行服务器断电了 —— **钱就凭空消失了。**

事务保证：这两步是一个不可分割的整体 —— 要么都生效，要么都不生效。

| | 说明 |
|---|---|
| `commit()` | 确认这一组操作，永久生效 |
| `rollback()` | 撤销这一组操作，回到之前的状态 |

**阶段 3 只需要记住"改完要 commit"。** 事务的完整用法（`BEGIN` / `ROLLBACK`）以后做真实项目时会用到。

## 七、主键 与 `AUTOINCREMENT` —— 检测 C1 的答案

### 主键（PRIMARY KEY）是什么

**每行的唯一身份证。** 两条作用：

1. **唯一** —— 不允许重复（数据库强制，插重复会报错）
2. **快速定位** —— 数据库为它自动建索引（见第八节）

**没有主键会怎样？** 你无法可靠地"指认某一行"—— 如果有两条 `title` 和 `done` 完全一样，你能分清谁是谁吗？

### ⭐ `AUTOINCREMENT` 到底解决了什么

**一个很多人不知道的细节：**

| 写法 | 自增吗 | 会复用 id 吗 |
|---|---|---|
| `id INTEGER PRIMARY KEY` | ✅ 会自增 | ⚠️ **会复用**（删掉最大那行后，新行拿回同一个 id） |
| `id INTEGER PRIMARY KEY AUTOINCREMENT` | ✅ 会自增 | ✅ **永不复用** |

**SQLite 官方文档的说法**：`AUTOINCREMENT` 的唯一目的，就是**防止复用之前被删除行的 ROWID**。

### 这正好是检测 C1 那道题的答案

你的 `max(...) + 1` 相当于第一种 —— 它从"当前数据"算 id，删掉数据后 id 就会往回走。

```
你的方式：      删光 → max([]) + 1 = 1     ← id 1 被复用了
AUTOINCREMENT：  删光 → 计数器继续往上走    ← 新 id 是历史最大值 + 1
```

**危害（精确版）：**

| 危害 | 说明 |
|---|---|
| 分享的链接 | `/todos/1` 两分钟后指向**另一条任务** |
| 日志追溯 | "删除 id 1" 和 "修改 id 1" **分不清是不是同一个对象** |
| 关联数据 | 以后加评论表存 `todo_id`，会**挂到错误的任务上** |

> **阶段 3 会亲手验证这件事**：删光所有任务，再新增一条，看 id 是不是 1。
> **这次是用手记住的，不是用脑记的。**

## 八、索引：你在数据结构课上学过它

**为什么 `SELECT * FROM todos WHERE id = 5` 很快？**

因为主键**自动建了索引**。

| | 没有索引 | 有索引 |
|---|---|---|
| 查找方式 | **全表扫描** —— 逐行比较 | 直接定位 |
| 复杂度 | **O(n)** | **O(log n)** |

**索引的底层结构是 B+ 树。** 数据结构课上学的那个 —— 为了数据库和文件系统而设计的多路平衡树。

> **类比 C 语言**：
> - 无序数组里找元素 → 线性查找 O(n)，得一个个比
> - 有序数组里找元素 → 二分查找 O(log n)
>
> **索引 = 给数据库预先建好的"有序目录"。**

**代价**：索引占空间，而且每次 `INSERT` / `UPDATE` 都要维护它（**写变慢**）。

> **这就是为什么不能"给每一列都建索引"** —— 查询快了，写入慢了，空间也涨了。**又一个权衡。**

**阶段 3 不用建索引**（主键自带的就够了）。

## 九、SQLite 的三个特点

### ① 它是一个库，不是一个服务器

| | MySQL / PostgreSQL | **SQLite** |
|---|---|---|
| 形态 | **独立进程**，装好、启动、配账号密码 | **一个库文件**，直接被程序调用 |
| 数据在哪 | 服务器管理的目录 | **就一个 `.db` 文件** |
| 需要安装吗 | 要 | **不要**（Python 自带） |

**所以不需要"启动数据库服务"** —— 程序直接打开 `todos.db` 文件就能读写。这是它最适合入门的原因。

**代价**：并发写能力弱（同一时刻只能一个写入者）。学习项目和中小型应用完全够。

### ② SQL 语法和 MySQL / PostgreSQL 基本通用

**你学的是 SQL，不是 SQLite。** 换数据库时，**90% 的语句不用改**。

差别主要在类型名、自增写法、一些高级特性上。**你不是在学一个即将过时的工具。**

### ③ ⚠️ SQLite 是"弱类型"的

**对一个 `INTEGER` 列插入 `'abc'`，它可能不会报错**（会尝试转换，转不了就按原样存）。

**这意味着：类型安全要靠你自己保证**（Pydantic 一层 + 读取时转换一层）。

> **这和 `"done":"False"` 那个教训是同一个主题的第三次出现。**
> 有些系统**不会替你拦截类型错误** —— 你得自己在边界上守住。

## 十、⭐ 一张串联表：把三个阶段的知识接起来

**这是最该记住的东西。**

| 你想要什么 | 阶段 2（Python 列表） | **阶段 3（SQL）** | HTTP |
|---|---|---|---|
| 拿全部 | `return todos` | `SELECT * FROM todos` | `GET /todos` |
| 找一条 | `for t in todos: if t["id"]==id` | `SELECT * FROM todos WHERE id = ?` | `GET /todos/{id}` |
| 新增 | `todos.append(new_todo)` | `INSERT INTO todos (...) VALUES (?, ?)` | `POST /todos` |
| 修改 | `t["done"] = True` | `UPDATE todos SET done = 1 WHERE id = ?` | `PUT /todos/{id}` |
| 删除 | `todos.remove(todo)` | `DELETE FROM todos WHERE id = ?` | `DELETE /todos/{id}` |

**看出来了吗 —— 三列是同一件事的三种表达。**

阶段 2 写的那 5 个接口，**逻辑一个字都不用改**，只是把"操作 Python 列表"换成"发 SQL 给数据库"。

> **所以阶段 3 不是重写项目，是给 5 个接口换一个更可靠的数据源。**

## 十一、速查表

### SQL 五句话

| 语句 | 作用 | 对应 HTTP | 只读？ |
|---|---|---|---|
| `SELECT` | 查 | `GET` | ✅ 是 |
| `INSERT` | 增 | `POST` | ❌ |
| `UPDATE` | 改 | `PUT` / `PATCH` | ❌ |
| `DELETE` | 删 | `DELETE` | ❌ |
| `CREATE TABLE` | 建表（一次性的） | — | ❌ |

### 三个必须记住的安全点

| 记住 | 因为 |
|---|---|
| **`UPDATE` / `DELETE` 必须先写 `WHERE`** | 否则全表遭殃，不可撤销 |
| **永远用 `?` 占位符，不要拼字符串** | 否则被 SQL 注入 |
| **改完必须 `commit()`** | 否则数据没真的写进去，而且不报错 |

### 类型对照

| 层 | `done` 的类型 |
|---|---|
| HTTP / JSON | `true` / `false` |
| Python | `True` / `False` |
| **SQLite** | **`1` / `0`（没有布尔类型！）** |
