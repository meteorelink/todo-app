# 07 · 从"解析"到"动手"：工具调用、幂等与成本

> 这一篇对应阶段 8.5 / 8.6。
> 前面 8.3–8.4 做的是"让模型**说**出结构化数据，人来确认"；
> 这里做的是"让模型**自己决定做哪几步**"。
> 差别不在模型能力，在**中间那个"人"被换成了代码循环**。

---

## 一、两个接口，两种信任程度

我们最后有两个 AI 接口，长得像，脾气完全不同：

| | `POST /ai/parse` | `POST /ai/agent` |
|---|---|---|
| 谁决定"要做什么" | 我们的代码（写死：解析成任务） | 模型（读工具说明后自己挑） |
| 一次请求里能发生几步 | 1 | 最多 `MAX_TURNS = 5` 轮 |
| 会写数据库吗 | **不会**，只给草稿 | **会**，当场执行 |
| 失败怎么表现 | 一个异常 → 一个状态码 | 可能"做了一半" → 200 + `truncated` |
| 用户要不要确认 | 要（预览 → 确认创建） | 不要（除了删除） |

⚠️ 这两条路都**保留**，没有谁替代谁。
理由不是技术，是**用户性格**：同一句"买牛奶"，
有人想先核对一遍，有人嫌麻烦想直接建。
"要不要先让我看一眼"是用户的决定，不该让模型猜。

## 二、工具调用到底是什么：一个 `while` 循环

先把最重要的一句话说完：

> **模型不会执行任何东西。**

它只会输出一段文本形状的东西：

```json
{"tool_calls": [{"id": "call_1", "function": {"name": "create_todo", "arguments": "{\"title\":\"买牛奶\"}"}}]}
```

真正把任务写进数据库的，是**你写的那个函数**。
所谓"模型调用工具"，准确说法是：

> 模型说"我想调 `create_todo`，参数是这个"，
> 你的代码看到这句话，决定**执行还是不执行**，然后把结果**喂回去**，再问一次。

`ai_agent.run_agent()` 的骨架就只有这么点东西：

```python
for turn in range(1, MAX_TURNS + 1):
    data = ai_client.chat(messages, api_key, tools=TOOL_SCHEMAS)

    message = ai_client.get_message(data)
    calls = ai_client.get_tool_calls(data)

    if not calls:                       # 它不想调工具 → 说完了
        return AgentResult(reply=message["content"], ...)

    messages.append({"role": "assistant", "content": message["content"] or "", "tool_calls": calls})

    for call in calls:                  # 它想调，我来执行
        action, tool_content, raw = _execute_call(call)
        messages.append({"role": "tool", "tool_call_id": call["id"], "content": tool_content})
```

⭐ 三件看起来像"智能"的事，其实**没有一行新代码**，全是这个循环长出来的：

1. **它自己决定要不要先查** —— "把买牛奶标成完成"这句话里没有 id，
   它得先 `list_todos` 才知道 buy 牛奶是 30 号。
2. **它自己决定顺序** —— 查 → 改，还是直接改。
3. **它自己判断失败** —— 看到 `"任务不存在"` 会换个 id 再试，或者告诉你做不到。

## 三、协议三件套：`tool_calls` / `tool_call_id` / `role: tool`

一次工具调用在 `messages` 里留下**两条**记录，缺一不可：

```python
# ① 模型的"申请单"：原样回填，一个字都不能改
{"role": "assistant", "content": "", "tool_calls": [{"id": "call_1", "type": "function",
 "function": {"name": "create_todo", "arguments": "{\"title\":\"买牛奶\"}"}}]}

# ② 工具的执行结果：必须带 tool_call_id，指明这是给哪张申请单的答复
{"role": "tool", "tool_call_id": "call_1", "content": "已创建 #30《买牛奶》"}
```

⚠️ 三个最常见的坑：

- **`arguments` 是字符串，不是 dict。** 直接 `call["function"]["arguments"]["title"]`
  会炸 `TypeError: string indices must be integers`。先 `json.loads`，
  而且它**可能不是合法 JSON**（模型会写错逗号、会加注释）—— 这就是必须 `try` 的原因。
- **漏了 `tool_call_id`**，下一次请求会被上游直接拒掉：有申请单没有答复，对话不完整。
- **把 `reasoning_content` 一起回填**。我们只保留 `role / content / tool_calls` 三个字段，
  理由见 `ai_agent.py` 里那段注释：思考过程不是对话的一部分，塞回去只会让下一轮更贵、更乱。

## 四、`description` 不是注释，是**给模型看的说明书**

对比一下这两套"路由表"：

```
FastAPI:  "GET /todos/23"  → 查路由表 → get_todo(id=23)
工具调用:  "create_todo"    → 查 TOOL_TABLE → _tool_create_todo(args)
```

**同一张表，换了谁来查。**

区别在于：FastAPI 的匹配规则是**写死**的（路径、方法），
而工具的选择是**模型读完 `description` 后自己判断**的。

所以 `description` 里写的每一句都在影响行为。比如我们写进
`request_delete` 的那句：

> "**不会真的删除**：只是把删除请求提交给用户，必须由用户在界面上点确认才会执行。"

模型读完就知道：调完不能跟用户说"已删除"，得说"要删吗"。
这不是修辞，这是**行为约束**。

## 五、幂等：给人和给模型的接口，应该不一样

这是 8.5 里唯一一次"推翻已完成的代码"。

原来给模型的工具是 `toggle_todo`（切换完成状态），它有个致命问题：

```
toggle(30) → 完成
toggle(30) → 又变回未完成        ← 执行两次，回到原点
```

模型重试、用户连点、网络重发 —— 任何一种都会让它执行两次。
更要命的是它**表达不出**"把这条改回未完成"，只能靠"猜它现在是完成还是未完成"。

所以：

| | 谁在用 | 语义 | 调两次的结果 |
|---|---|---|---|
| `POST /todos/{id}/toggle` | 界面上的按钮 | 翻转 | 回到原点 ✗ |
| `set_done(id, done)` | 模型 | 设为某个值 | 还是那个值 ✓ |

**判据是"调用方会不会重试"**：人看着状态点按钮，不会连点；
模型会重试、会并行、会犯迷糊 —— 所以给它的接口必须**幂等**。

实现上有个小坑：`set_done` 幂等之后，怎么区分"改成了一样的值"和"这条根本不存在"？

```python
cur = conn.execute("UPDATE todos SET done = ? WHERE id = ?", (int(done), id))
changed = cur.rowcount
if changed == 0:
    raise HTTPException(status_code=404, detail="任务不存在")
```

实测：同一行连做 3 次 `SET done = 1` → `rowcount` 是 `1, 1, 1`；不存在的 id → `0`。

> **SQLite 的 `rowcount` 是"WHERE 匹配到几行"，不是"值变了几行"。**

顺带一个跨库差异（面试常问）：MySQL 默认（未开 `CLIENT_FOUND_ROWS`）的
`affected_rows` 是"**真的变了**的行数"，同样的代码在 MySQL 上会把
"我已经是完成状态了"误报成 404。

## 六、销毁性操作：给的不是"工具"，是"意图"

模型能不能删任务？这是一个产品问题，不是技术问题。三种选择：

| 方案 | 后果 |
|---|---|
| A. 给 `delete_todo` | 一句"把没用的都清掉"就能静默删光，**不可挽回** |
| B. 完全不给 | 产品像残废；而且必然出现"我没有删除权限"这种坏话术 |
| **C. 给，但要人点头** | 和其他成熟 agent 一致 |

我们选 C。实现方式很关键 —— **不是**给模型一个 `delete_todo` 然后祈祷它不乱调：

```python
def _tool_request_delete(args) -> dict:
    todo = todos_router.read_one_todo(args.id)      # 查一下确实存在
    return {"id": todo["id"], "title": todo["title"], "deleted": False,
            "note": "已把删除请求提交给用户，尚未删除。"}
    # ↑ 这里没有 DELETE，一行都没有
```

删的动作最后发生在**前端那个红色按钮**上，它调的是 `DELETE /todos/{id}` ——
和列表里那个"删除"按钮**完全同一条路**。整条 agent 链路上，模型从没碰过删除。

### 为什么"确认"必然等于"把一次请求拆成两次"

因为 HTTP 是**一问一答**的：后端在一条请求里**没有办法中途停下来问用户**。
（技术上能做 WebSocket / SSE / 长轮询，但那是另一套复杂度。）

所以：
- `/ai/parse` 出草稿，`/todos/batch` 才写库 —— 这是 8.4 已经做过的同样的拆分；
- `/ai/agent` 出 `proposals`，前端点"删除"才真的删 —— 同一招，用第二次。

> **销毁性操作不需要"工具"，需要"意图"。**
> 模型能做的只是**提议**。

### 界面上也必须分开

`AgentResult` 里 `actions` 和 `proposals` 是两个字段，不是懒得合并：

- `actions` = **已经发生的事**，前端只能显示（灰的、小的、带 ✓）
- `proposals` = **还没发生的事**，前端要问（红框、黄底、带按钮）

如果塞进同一个数组，界面就会长成：

```
✓ 请求删除 #30《买牛奶》
```

用户扫一眼"✓"，以为删完了，刷新发现还在 —— **这比不显示更糟**。

## 七、成本：这个功能为什么天生贵

先看结构，再看数字。

**一轮 = 一次完整的 API 请求**，而且 `messages` 每轮都在变长：

```
第 1 轮：system + user                      = 200 tokens
第 2 轮：上面的 + assistant + tool           = 300 tokens
第 3 轮：再 + assistant + tool               = 400 tokens
```

一次"3 轮"的任务，你付的是 `200 + 300 + 400 = 900`，
而不是 `400`。**同一段对话被重复计费了三次。**

再加上我们实测到的两件事：

1. **思考 token 占输出的大头**（实测 65%–90%），而且波动极大（9 → 1314）。
2 . **`prompt_cache_hit_tokens` 一直是 0** —— 连发一模一样的请求也不命中，
   所以"缓存能帮我省钱"这个假设在我们的场景里不成立。

### 我们实际装了六道闸门

| 闸门 | 位置 | 挡住什么 |
|---|---|---|
| 工具只有 4 个、`description` 简短 | `TOOL_SCHEMAS` | 每轮固定开销 |
| `MAX_TURNS = 5` | `run_agent` | 死循环 / 无限账单 |
| 参数错误也消耗轮次 | `run_agent` | 反复拼错参数 |
| `MAX_INPUT_CHARS = 2000` | 后端 `ParseRequest` | 超长输入 |
| `maxLength={2000}` | 前端 `App.jsx` | 手滑（连等都不用等） |
| 按钮 `disabled` | 前端 | 连点三次 = 三次执行 = 三次收费 |

⚠️ 最后一道其实很弱，得说实话：**我们没有"用户"这个概念**，
所以挡得住手滑，挡不住换浏览器再来的人。
真要按人限流，得先有身份系统（登录 / token），那是另一个阶段的事。

### 少见的那个坑：把失败也当成本

`MAX_TOKENS = 800` 那次教训还在：它并没有触发。
真正让成本失控的不是单次上限太小，而是**重试次数没有上限**。
所以现在的分工是：

> 单次上限给足（2000，宁可多花一点也别截断），
> 真正的天花板交给 `MAX_ATTEMPTS = 3` / `MAX_TURNS = 5`。

## 八、注入防护：这一层拦不住，只能缩小爆炸半径

先说结论，免得抱错期望：

> **prompt injection 无法像 SQL 注入那样被"修好"。**

因为 SQL 注入的根因是"数据和指令共用一条通道"，参数化查询把它们彻底分开。
而大模型的整个工作方式，就是**把一段自然语言当成指令来解释**。
"用户的话"和"用户的指令"在模型眼里是同一种东西 —— 这不是实现缺陷，是原理。

所以能做的只有降低**最坏情况**：

| 手段 | 在我们的代码里 |
|---|---|
| **最小权限** | 工具表里没有删除；`set_done` 只能改 `done` 一个布尔值 |
| **参数白名单** | `priority` 用 `Literal["high","normal","low"]`，不是自由字符串 |
| **结构化输出** | 模型只能产出 `{title, due, priority}`，产不出 SQL |
| **人在环** | 删除必须人点；草稿必须人点"确认创建" |
| **出错不转发原文** | 上游 401 里有 key 片段，只进日志，永远不进响应体 |

⚠️ 有一条**不要做**：用关键词拦注入。

```python
if "忽略" in text:  # ❌ 纸糊的防线
    return 400
```

绕过它只需要换个说法（"忘掉上面那些要求"），而它会把正常人误伤一片
（"忽略这条已完成的"）。**拦不住的东西，就不要假装拦住了** ——
假装拦住比不拦更危险，因为你会因此放松真正有效的那几层。

## 九、面试可以这样讲（都来自这个项目）

1. **"你项目里的 agent 是怎么实现的？"**
   → 一个 `for` 循环 + 一张工具表。模型输出 `tool_calls`，
   我执行后把结果作为 `role: tool` 消息喂回去，直到它不再调工具或到轮次上限。
   没有框架，大约 100 行。

2. **"怎么防止模型乱删数据？"**
   → 工具表里根本没有删除。模型只能调 `request_delete`，
   它只做一次查询然后返回"待确认"；真正的 `DELETE` 由前端按钮触发，
   和普通删除按钮走同一个接口。**权限在代码里，不在提示词里。**

3. **"为什么 agent 的成本比单次对话高很多？"**
   → 每轮都是一次完整请求，`messages` 单调变长，同一段上下文被重复计费；
   加上推理模型的思考 token 可以占输出的 70%+。
   所以工具要少、轮次要限、输入要短。

4. **"为什么给模型的接口是 `set_done` 而不是 `toggle`？"**
   → 幂等。模型会重试、会并行，`toggle` 执行两次会回到原点。
   `set_done` 连调三次结果不变，而且能表达"改回未完成"。

5. **"工具执行失败了怎么办？"**
   → 分两类。模型能改的（参数写错、id 不存在、JSON 不合法）**不抛异常**，
   变成一条 `tool` 消息喂回去让它自己修；模型改不了的（数据库挂了、上游 401）
   直接抛，映射成 500/502。
   原则：**模型能改的错误喂回去，改不了的抛出去。**

6. **"怎么防 prompt injection？"**
   → 先承认防不住，再讲缩小爆炸半径：最小权限、参数白名单、
   人在环确认、不转发上游错误原文。并且明确说**不用关键词黑名单**，以及为什么。
