## 一、HTTP 的本质：约定好的纯文本

先破除神秘感：**HTTP 不是什么库、不是函数、不是某个 API，它只是一套"大家说好用这个格式聊天"的文字约定。**

它规定了两件事：

1. 客户端发给服务器的**那段文字长什么样**
2. 服务器回给客户端的**那段文字长什么样**

就这么简单。打开浏览器的 F12，其实就能看到这些纯文本。

**类比**：在 C 里写 `int add(int a, int b)`，编译器不会替你发明规则，它遵循一个**调用约定**（cdecl / stdcall）——参数怎么压栈、谁负责清理栈。双方都遵守，才能对接上。

HTTP 就是 Web 世界的调用约定。区别在于：

| | 函数调用 | HTTP |
|---|---|---|
| 距离 | 同一个进程内存里 | 跨网络、跨机器 |
| 传递方式 | CPU 寄存器 / 栈 | TCP 连接上的一串字节 |
| 约定内容 | 参数压栈顺序 | 那串字节的文本格式 |

> **记住"它是文本"，后面 90% 的疑问都能自己推出来。**

## 二、一次通信的原始样子（本节最重要）

假设浏览器要拿任务列表，它在 TCP 连接上发出去的**就是这样一段普通文本**：

```http
GET /todos HTTP/1.1
Host: 127.0.0.1:8000
User-Agent: Mozilla/5.0
Accept: application/json

```

服务器回过来的，**也是这样一段文本**：

```http
HTTP/1.1 200 OK
content-type: application/json
content-length: 42

[{"id":1,"title":"写实验报告","done":false}]
```

**没有魔法。** 你能读、能背、能手写。

### 请求的第一行 = 三样东西

```
GET /todos HTTP/1.1
 │     │        └── 协议版本（现在几乎都是 1.1 或 2）
 │     └── 路径：我想要哪个资源
 └── 方法：我想干什么
```

### 请求的第二行开始 = Header（元数据）

```
Host: 127.0.0.1:8000        ← 我要找的是哪台机器上的哪个服务
User-Agent: Mozilla/5.0     ← 我是谁（什么浏览器/程序）
Accept: application/json    ← 我希望你用什么格式回答我
```

### 那个空行，是一条分隔线 ⚠️

**Header 结束、Body 开始，就是靠一个空行分界。**

这个细节能解释很多诡异问题：如果手工构造请求时忘了这个空行，服务器会把 body 当成又一个 header，然后一脸茫然。

### 响应的第一行 = 状态码

```
HTTP/1.1 200 OK
        └── 200 是给程序看的，OK 是给人看的
```

### 真正的内容在最后

```
[{"id":1,"title":"写实验报告","done":false}]
```

这行叫 **Body（响应体）**。前面那一坨都是"关于这封信的说明"，**只有这里才是信的内容**。

**关键认知**：`content-type: application/json` 这个 header 是在告诉对方——"我给你的这堆字节，请按 JSON 去解释"。

因为**底层只是字节流**，如果没有这个说明，对方根本不知道收到的是 JSON、HTML 还是图片。这跟 C 里 `void*` 指针必须配一个类型信息才能正确解释是同一个道理。

## 三、方法（动词）：语义约定，不是强制

| 方法 | 语义 | 对应待办的什么操作 | 幂等？ |
|---|---|---|---|
| `GET` | 读取 | 查看任务列表 | ✅ 是 |
| `POST` | 新建 | 新增一个任务 | ❌ 否 |
| `PUT` | 整体替换 | 改一个任务的**全部字段** | ✅ 是 |
| `PATCH` | 局部修改 | 只把 `done` 改成 true | ✅ 是 |
| `DELETE` | 删除 | 删掉一个任务 | ✅ 是 |

### 幂等是什么意思（这个概念其实已经会了）

数学上 `f(f(x)) = f(x)`。HTTP 里叫**幂等（idempotent）**：**同一个请求发一次和发十次，服务器的最终状态一样。**

- `DELETE /todos/1` 发十次 → 结果都是"1 号任务没了" ✅ 幂等
- `POST /todos`（新建"写作业"）发十次 → **会得到十个"写作业"** ❌ 不幂等

**这直接解释了一个肯定遇到过的现象**：

> 为什么刷新一个刚提交过表单的页面，浏览器会弹窗问"要重新提交吗？"

因为刷新 = 重发上一次的 `POST`，而 `POST` 不幂等，浏览器怕重复下单 / 重复发帖，所以拦一下。

### 一个重要提醒

**这些方法名是"约定"，不是"技术强制"。** 完全可以写一个 `GET /delete-everything` 来删数据，服务器也会照做。

那为什么必须守规矩？因为**全世界有无数中间设施靠这些约定工作**：

- 浏览器缓存（只缓存 GET）
- 搜索引擎爬虫（只爬 GET，绝不点 POST，否则会删数据）
- 公司防火墙、CDN、负载均衡器

破坏约定，它们就误解你。

> **这就是"RESTful"这个词的全部含义**：按大家的约定来设计接口。

## 四、URL 解剖

```
http://127.0.0.1:8000/todos/1?done=true
  │         │      │     │        └── 查询参数 Query String
  │         │      │     └── 路径 Path
  │         │      └── 端口
  │         └── 主机（这里是本机）
  └── 协议
```

### 两类参数，后面 FastAPI 会反复用到

**路径参数（Path Parameter）——"我要哪个东西"**

```
/todos/1     ← 1 号任务
/todos/2     ← 2 号任务
```

它是**资源标识**，回答"是哪一个"。所以在 FastAPI 里写成 `/todos/{id}`。

**查询参数（Query String）——"我要怎么筛"**

```
/todos?done=true            ← 只看已完成的
/todos?done=false&limit=10  ← 只看未完成的，且最多 10 条
```

它以 `?` 开始，多个用 `&` 连接，回答"怎么过滤/排序/分页"。

**怎么区分**：问自己"这个值是不是在指定'哪一个具体对象'？"是 → 路径参数；只是筛选条件 → 查询参数。

### 关于端口

端口号的作用可以直接类比**文件描述符**——同一台机器（同一个 IP）上要跑很多服务，端口就是区分"这封信该送给哪个程序"的编号。

`127.0.0.1` 是**回环地址**，专指"本机"。所以 `http://127.0.0.1:8000` 的意思是：**我自己这台机器上，监听 8000 端口的那个程序**。

**别人访问不了它**——这也是为什么阶段 7 要部署到服务器上，别人才能打开。

> `localhost` 和 `127.0.0.1` 基本是一回事。

## 五、状态码：先记大类，再记细节

**第一位数字就是大类**：

| 范围 | 含义 | 记法 |
|---|---|---|
| `1xx` | 信息，很少见 | 忽略 |
| `2xx` | **成功** | 好事 |
| `3xx` | **重定向**，去别处 | 你搬家了 |
| `4xx` | **客户端的错** | **你（请求方）错了** |
| `5xx` | **服务器的错** | **我（后端）崩了** |

### ⭐ 4xx 和 5xx 的区别，是调试时最重要的判断依据

- 看到 `4xx` → **问题在请求方**：路径写错了？数据格式不对？没登录？
- 看到 `5xx` → **问题在后端代码**：Python 抛异常了，去看后端终端里的报错

这一条能省下大量弯路。很多新手看到报错就乱改代码，其实压根是请求发错了。

### 最常遇到的几个

| 码 | 名字 | 什么时候出现 |
|---|---|---|
| `200` | OK | 成功 |
| `201` | Created | 成功创建了新资源（规范的 POST 应该返回它） |
| `400` | Bad Request | 传的数据不合法（业务层面） |
| `401` | Unauthorized | **没登录** |
| `403` | Forbidden | **登录了，但没权限** |
| `404` | Not Found | **路由表里没有这条规则**（见第九节） |
| `422` | Unprocessable Entity | **传的数据格式不对**（FastAPI 自动返回这个） |
| `500` | Internal Server Error | 后端代码抛异常了 |

> **401 vs 403**：401 = "你是谁？" 403 = "我知道你是谁，但你不许进。"

> **404 vs 422**：404 = "这个路径我没有"；422 = "路径对，但数据解析不了"。阶段 1 会亲眼看到——故意传错类型的数据，FastAPI 自动返回 422 加详细说明。

## 六、Header：为什么把"说明"和"内容"分开

Header 就是一堆 `键: 值` 的元数据。常见的有：

```
Content-Type: application/json      ← 内容的格式
Content-Length: 42                  ← 内容有多长（字节）
Authorization: Bearer xxxxx         ← 身份凭证
Accept: application/json            ← 我希望你回什么格式
Cookie: sessionid=abc123            ← 客户端带上来的"取衣单"（见第八节）
```

**这个设计为什么好？** 因为它是**可扩展的**。以后需要新功能，加一个新的 header 名就行，**协议语法一个字都不用改**，老程序看到不认识的 header 直接忽略即可。

这跟"给结构体加字段但保持向后兼容"是同一个设计思路。对比一下：如果 HTTP 把格式写死成固定几个位置，那每加一个功能都要改协议版本，全世界都得跟着升级——网络效应的噩梦。

## 七、Body 与 JSON：为什么不直接传结构体

**Body 才是真正的内容**。约定上：

- `GET` 通常**没有** body（要的东西在 URL 里描述）
- `POST` / `PUT` / `PATCH` **有** body（要提交的数据）

**为什么用 JSON，而不是直接把 C 的结构体 `memcpy` 出去发过去？**

因为会有一堆问题：

| 问题 | 说明 |
|---|---|
| 字节序 | 你的机器小端，对方大端，数字全错 |
| 内存对齐 | 结构体里可能有 padding，对方不知道 |
| 指针 | 结构体里有指针就完蛋，传过去是个无意义的地址 |
| 类型尺寸 | `long` 在 Windows 是 4 字节，Linux 是 8 字节 |
| 语言差异 | 对方用的是 Python，根本没有"结构体"这东西 |

JSON 是**文本**，绕开了以上全部问题：任何语言、任何机器都能读写，而且**人眼可读**——这一点在调试时值千金。

**代价**：文本比二进制大、解析更慢。这是"通用性 vs 性能"的经典权衡。（性能敏感场景会用 Protobuf 这类二进制格式，那是后话。）

## 八、无状态（Stateless）：最重要的一个概念

### 8.1 先说清楚"状态"是什么

**状态 = 程序为了处理"下一个请求"而必须记住的信息。**

比如：你刚才登录了，下一个请求服务器得知道"这是张三"——**"你是张三"就是状态。**

- **有状态服务器** = 把这些信息**存在自己的内存里**
- **无状态服务器** = **什么都不记**，你的每个请求都必须**自带全部所需信息**

> **HTTP 协议本身就是无状态的。** 这不是可选设计，是它从第一天就定下的规矩。

### 8.2 生活例子：你妈 vs 银行柜员

**有状态：你妈。**

你妈记得你生日、你爱吃红烧肉、你对花生过敏。你回家不用开口她就知道该做什么。

听起来很棒，但：

- 你妈**只有一个**。她要是生病了（服务器宕机），你就没人管了。
- 想给你也配一个妈分担压力？（加服务器）新妈**不认识你**，你得从头跟她培养感情。

**这就是有状态服务器的困境**：状态只存在于那台机器里。机器一挂，状态全丢；想加机器，新机器什么都不认识。

**无状态：银行柜员。**

你去任何一个网点、找任何一个柜员，他**都不认识你**。但他刷一下你的身份证，就能从**系统**里查出你的一切。

- 柜员换来换去都无所谓——**记忆不在柜员脑子里，在系统里。**
- 这个网点排队太长？去隔壁网点，一样能办事。
- 柜员突然辞职（服务器重启）？你的存款一分不少。

**ATM 机是更极端的例子**：它完全不需要认识你，但凭卡和密码就能给你钱。**任何一台 ATM 都能服务你。**

> **无状态服务器的本质：它把"记忆"从自己的脑子里搬到了别处（数据库）。**

### 8.3 程序员的类比：依赖全局变量的函数 vs 纯函数

这个类比最精准。有 C/C++ 基础的话应该立刻能感受到痛：

```c
// ❌ 有状态：依赖全局变量
User g_current_user;   // 全局的"当前用户"

void handle_request(Request req) {
    if (g_current_user.id == 0) return error(401);
    // ...用 g_current_user 干活
}
```

这段代码的毛病：

- **非线程安全**：两个请求同时进来，`g_current_user` 会被互相覆盖，张三的请求可能读到李四的身份
- **不可重入**
- **没有那个全局变量，这函数根本跑不起来**

```c
// ✅ 无状态：所有信息通过参数传入
void handle_request(Request req, User current_user) {
    // 当前用户是谁，请求方自己告诉我
}
```

这就是**纯函数**：输出只依赖输入。所以：

| | 有状态服务器 | 无状态服务器 |
|---|---|---|
| 类比 | 依赖全局变量的函数 | 纯函数 |
| 能否并行处理 | ❌ 会串数据 | ✅ 天然安全 |
| 能否多开进程 | ❌ 冲突 | ✅ 随便开 |
| 重启后 | 状态丢失 | 无影响 |

> **记住这句话："无状态服务器 = 纯函数"。** 后面全通。

### 8.4 图解：为什么无状态才活得下去

**有状态的做法：**

```
        用户A ──┐
                ├──→ 服务器（内存里记着 A 和 B 的购物车）
        用户B ──┘

❌ 服务器重启 → 所有人的购物车瞬间清空
❌ 用户多了要加服务器？
        用户A ──┐                    ┌──→ 服务器1（记着 A 的购物车）
                ├──→ 负载均衡 ──┤
        用户B ──┘                    └──→ 服务器2（记着 B 的购物车）

   但负载均衡是"随机分"的！A 的下一个请求可能被分到服务器2
   → 服务器2：你是谁？你的购物车是空的。
```

**无状态的做法：**

```
        用户A ──┐                    ┌──→ 服务器1 ──┐
                ├──→ 负载均衡 ──┤               ├──→ 数据库
        用户B ──┘                    └──→ 服务器2 ──┘
                                      （共享的"记忆"）

✅ 请求发给哪台机器都一样，因为记忆在数据库里，不在服务器里
✅ 服务器1 挂了？把请求全给服务器2 就行，用户毫无感知
✅ 要扩容？直接多开 10 台，不需要做任何配置
```

**这就是"可水平扩展（scale out）"的全部秘密。** 也是为什么所有大型网站都必须走无状态这条路——用户上亿的时候，你不可能让每个人都绑死在一台机器上。

### 8.5 那"记住你是谁"到底怎么办？

既然服务器不记，那只能**把状态外移**。两个去处：

**去处一：放在客户端手里 —— 这就是 Cookie**

**干洗店的比喻**：干洗店不需要记得你是谁。它给你一张**取衣单**，你下次凭单子来取。单子丢了，衣服就取不出来。

HTTP 里这张"取衣单"就是 **Cookie**：

```
你第一次登录
  ──→ 服务器验证密码通过，生成一个随机字符串 abc123
  ──→ 响应里带上：Set-Cookie: sessionid=abc123

你之后的每一个请求
  ──→ 浏览器自动带上：Cookie: sessionid=abc123
  ──→ 服务器拿 abc123 去数据库查："哦，这是张三"
  ──→ 处理完，又忘了（下次还得靠 Cookie 提醒）
```

**去处二：放在共享存储里**

数据库、Redis 这类可以被所有服务器访问的地方。这样即使有 10 台服务器，大家查的也是同一份数据。

### 8.6 由此能解释的日常现象

| 现象 | 原因 |
|---|---|
| **清除浏览器 Cookie 会导致退出登录** | 那张"取衣单"被扔了，服务器再也认不出你。**不是服务器把你忘了——它本来就没记过你** |
| 换个浏览器就要重新登录 | Cookie 是存在浏览器里的，另一个浏览器手上没有单子 |
| 无痕模式关掉窗口就退出登录 | 无痕模式的 Cookie 在窗口关闭时清空 |
| 服务器重启后购物车还在 | 购物车存在数据库里，不在服务器内存里 |

### 8.7 这直接决定了项目架构

阶段 1、2 里，代码会是这样：

```python
todos = []   # ← 把任务存在一个 Python 列表里
```

**这是个有状态的服务器**（准确说：把状态放在了最不可靠的地方）。它的问题：

| 问题 | 后果 |
|---|---|
| 服务器重启 | 所有任务消失 |
| 以后要多开几台服务器 | 每台各有一份，用户看到的数据不一样 |
| 部署到线上 | 平台随时可能重启你的进程，数据说没就没 |

所以结论不是"老师说要学数据库"，而是：

> **因为 HTTP 无状态 + 服务器内存不可靠，所以数据必须放到一个"所有请求都能访问、且重启不丢"的地方。那个地方就叫数据库。**

阶段 3 做的就是这个。**等阶段 2 亲手重启服务器、看到任务全没了，这个道理会刻进骨头里。**

### 8.8 小结

| 要点 | 内容 |
|---|---|
| 是什么 | 服务器不记得你，每个请求必须自带全部所需信息 |
| 好处 | 可水平扩展、天然并行安全、重启无影响 |
| 代价 | "记住你是谁"必须靠额外机制实现 → Cookie / Token / 数据库 |
| 一句话 | **无状态服务器 = 纯函数** |
| 对你的影响 | 数据不能放内存变量里，**必须进数据库** |

## 九、路由表：请求如何找到你的函数

### 9.1 生活例子：医院的导诊台

你进医院说"我要看牙"，导诊台说"3 楼口腔科"。

**导诊台不给你看牙。她只做一件事：查一张表。**

```
症状/科室  →  去哪
牙疼       →  3 楼口腔科
骨折       →  1 楼急诊
皮肤问题   →  5 楼皮肤科
```

**路由表就是这张登记表。** 它自己不含任何业务逻辑，只负责"来的请求该交给谁"。

FastAPI 里，`@app.get("/todos")` 这一行干的事情就是：

> **往登记表里写一行：「收到'方法=GET、路径=/todos'的请求时，交给下面这个函数处理。」**

### 9.2 如果不给你框架，用 C 你会怎么写

这才是最扎实的理解方式。**假设让你纯用 C 写一个 Web 服务器的分发逻辑：**

```c
typedef Response (*Handler)(Request);

typedef struct {
    char   *method;
    char   *path;
    Handler fn;
} Route;

// 这张表就是"路由表"
Route routes[] = {
    { "GET",    "/todos",      get_todos    },
    { "POST",   "/todos",      create_todo  },
    { "GET",    "/todos/{id}", get_one_todo },
    { "DELETE", "/todos/{id}", delete_todo  },
};

Response dispatch(Request req) {
    for (int i = 0; i < ROUTE_COUNT; i++) {
        if (strcmp(req.method, routes[i].method) == 0 &&
            path_match(req.path, routes[i].path)) {
            return routes[i].fn(req);      // 找到了 → 调用
        }
    }
    return not_found();                    // 循环跑完都没匹配 → 404
}
```

**这就是路由表的全部真相。没有魔法，就是一个数组 + 一个循环。**

### 9.3 FastAPI 的装饰器 = 往数组里追加一行

现在看 FastAPI 的写法：

```python
@app.get("/todos")
def read_todos():
    ...
```

**它做的事情，完全等价于往上面那个 `routes[]` 数组里追加一行：**

```c
{ "GET", "/todos", read_todos },
```

装饰器 `@app.get("/todos")` 只是一层**语法糖**——它让你把"注册路由"和"写处理函数"写在同一个地方，代码更集中。

### 9.4 图解：一个请求是怎么变成函数调用的

```
   收到请求：  GET /todos
                  │
                  ▼
   ┌──────────────────────────────────────┐
   │            路由表（本质上是个字典）      │
   ├──────────┬──────────────┬────────────┤
   │  方法    │     路径      │    函数     │
   ├──────────┼──────────────┼────────────┤
   │  GET     │  /todos      │ read_todos │ ◄══ 匹配上了！
   │  POST    │  /todos      │ create_todo│
   │  GET     │  /todos/{id} │ get_one    │
   │  DELETE  │  /todos/{id} │ delete_one │
   └──────────┴──────────────┴────────────┘
                  │
                  ▼
         调用 read_todos()
                  │
                  ▼
         它以 Python 对象形式返回数据
                  │
                  ▼
         FastAPI 自动转成 JSON 文本
                  │
                  ▼
         HTTP/1.1 200 OK
         content-type: application/json

         [{"id":1,"title":"写实验报告","done":false}]
```

### 9.5 三个推论：解开你一定会遇到的谜团

#### 推论一：404 到底是从哪来的？

**就是那个循环跑完了，没有任何一行匹配上。**

```
请求：GET /todoss     ← 多打了一个 s

查表：GET /todos         ✗ 不匹配
      POST /todos        ✗ 不匹配
      GET /todos/{id}    ✗ 不匹配
      DELETE /todos/{id} ✗ 不匹配

      表里没有这一行 → 404 Not Found
```

**404 不是"文件不存在"，是"路由表里没有这条规则"。** 这一下就把第五节的状态码和这里串起来了。

（顺带一提：这也是为什么很多网站不管什么错误都返回 404 页面——它其实就是"我没这条路由"的通用兜底。）

#### 推论二：路径参数 `/todos/{id}` 是怎么工作的？

`{id}` 是一个**占位符**，表示"这一段可以是任何值"。

```
请求 GET /todos/1   →  匹配 GET /todos/{id}，并提取出 id = 1
请求 GET /todos/42  →  匹配 GET /todos/{id}，并提取出 id = 42
请求 GET /todos/abc →  也匹配，id = "abc"（类型对不对是后面校验的事）
```

**匹配成功时，把 `1` 抠出来当参数传给函数。** 所以函数签名写成 `def get_one_todo(id: int)`，那个 `id` 就是从这里来的。

这就是为什么路径参数不用手动解析 URL——**路由匹配的时候顺手就提取了**。

#### 推论三：为什么改了代码必须重启服务器？

**因为路由表是在"服务器启动的那一刻"一次性建好的。**

Python 加载 `main.py` 时会从上到下执行。执行到 `@app.get("/todos")` 时，这一行**立刻**把函数登记进路由表。全部执行完，表就定型了。

之后每来一个请求，只是**查这张已经建好的表**——它不会重新去读你的 `.py` 文件。

| 你改了什么 | 需要重启吗 | 为什么 |
|---|---|---|
| 路由定义（加接口、改路径） | ✅ **必须** | 表要重建 |
| 函数里的业务逻辑 | ✅ 通常也要 | 进程里跑的还是旧的代码对象 |

**这就是 `--reload` 参数的作用**：

```powershell
uvicorn main:app --reload
                  └────────┘
      监听文件变化，一改动就自动重启服务器
```

它在帮你自动完成"重启"这个动作。**但生产环境不会开 `--reload`**（每次改代码都重启，服务会抖），所以线上部署时得手动重启服务——阶段 7 会用到这个知识。

### 9.6 小结

| 要点 | 内容 |
|---|---|
| 是什么 | 一张"请求特征 → 处理函数"的映射表 |
| 等价物 | C 里的函数指针数组 + 一个遍历循环 |
| `@app.get("/todos")` | 就是往表里追加一行 |
| 404 的来源 | 表里查不到 |
| 路径参数 | 匹配时顺手把值抠出来传给函数 |
| 何时建表 | **服务器启动时**，所以改代码要重启（`--reload` 是自动重启） |

## 十、把两个概念合起来看：一次请求的完整旅程

现在看一个完整的请求，你应该能读懂每一步了：

```
浏览器：GET /todos/5
           │
           │  ① 无状态 → 请求必须自带一切
           │     所以如果这是需要登录的接口，
           │     Cookie: sessionid=abc123 会自动附上
           ▼
     Uvicorn 收到这段文本，解析
           │
           │  ② 路由表 → 查表
           ▼
     匹配到  GET /todos/{id}  →  get_one_todo
           │     并提取 id = 5
           ▼
     调用 get_one_todo(id=5, ...)
           │
           │  ③ 无状态 → 函数内部不能依赖任何内存里的旧状态
           │     它必须去数据库查："id=5 的那条任务是什么？"
           ▼
     数据库返回数据
           │
           ▼
     FastAPI 转 JSON → Uvicorn 拼响应文本 → 浏览器
```

**注意 ① 和 ③ 都是"无状态"逼出来的要求**：

- ① 请求必须自带身份信息（Cookie / Token）
- ③ 处理函数必须去**共享存储**取数据，不能靠内存缓存

**而 ② 是"路由表"**：把 URL 变成一次函数调用。

> **这两个概念，一个决定"数据放哪"，一个决定"请求去哪"。后面所有代码都在这两条主线上。**

## 十二、三个常见误解（提前排掉）

| 误解 | 事实 |
|---|---|
| "HTTP 是加密的" | ❌ **HTTP 是明文**。HTTPS 才加密，它是 HTTP 下面垫了一层 TLS。本地开发用 HTTP 完全没问题（因为不出本机） |
| "用 GET 还是 POST 取决于数据长度" | ⚠️ 民间流传的说法，不准确。**取决于语义**：读取用 GET，产生副作用用 POST。长度限制只是实现细节 |
| "服务器可以主动给我推消息" | ❌ HTTP 是**请求-响应**模式，**必须先有请求才有响应**，服务器不能主动开口。想要推送得用 WebSocket 或 SSE |

## 十三、一句话总结（速查表）

| 概念 | 一句话 |
|---|---|
| HTTP | 客户端和服务器之间**约定好的纯文本**对话格式 |
| 请求行 | 方法 + 路径 + 版本，回答"想干什么、对谁干" |
| 方法 | 语义约定，`GET` 读 / `POST` 增 / `PUT` 改 / `DELETE` 删 |
| 幂等 | 发一次和发十次效果一样；`POST` 不是，所以刷新会重复提交 |
| Header | 关于这封信的说明；**空行**是说明和正文的分界 |
| Body | 真正的正文内容，通常是 JSON |
| 状态码 | `2xx` 成功 / `4xx` 你的错 / `5xx` 我的错 |
| JSON | 跨语言、可读的文本数据格式，避开了字节序/对齐/指针的坑 |
| **无状态** | **服务器不记得你**；请求必须自带全部信息。等价于"纯函数"。**这是必须用数据库的根本原因** |
| **Cookie** | 客户端手里的"取衣单"，用来在无状态的协议上实现"记住你是谁" |
| **路由表** | "请求特征 → 处理函数"的映射表；`@app.get("/todos")` 就是往表里加一行 |
| **404** | 路由表里查不到这条规则 |
| 路径参数 | 路由匹配时顺手把 URL 里的值抠出来传给函数 |
| **启动时建表** | 路由表在服务器启动时建好，所以改代码要重启（`--reload` 自动重启） |
