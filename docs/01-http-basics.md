## 一、HTTP 的本质：约定好的纯文本

先破除神秘感：**HTTP 不是什么库、不是函数、不是某个 API，它只是一套"大家说好用这个格式聊天"的文字约定。**

它规定了两件事：

1. 客户端发给服务器的**那段文字长什么样**
2. 服务器回给客户端的**那段文字长什么样**

就这么简单。打开浏览器的 F12，其实就能看到这些纯文本。

**类比**：在 C 里写 `int add(int a, int b)`，编译器不会替你发明规则，它遵循一个**调用约定**（cdecl / stdcall）——参数怎么压栈、谁负责清理栈。双方都遵守，才能对接上。

HTTP 就是 Web 世界的调用约定。区别在于：

| | 函数调用 | HTTP |
|---|---|---|
| 距离 | 同一个进程内存里 | 跨网络、跨机器 |
| 传递方式 | CPU 寄存器 / 栈 | TCP 连接上的一串字节 |
| 约定内容 | 参数压栈顺序 | 那串字节的文本格式 |

> **记住"它是文本"，后面 90% 的疑问都能自己推出来。**

## 二、一次通信的原始样子（本节最重要）

假设浏览器要拿任务列表，它在 TCP 连接上发出去的**就是这样一段普通文本**：

```http
GET /todos HTTP/1.1
Host: 127.0.0.1:8000
User-Agent: Mozilla/5.0
Accept: application/json

```

服务器回过来的，**也是这样一段文本**：

```http
HTTP/1.1 200 OK
content-type: application/json
content-length: 42

[{"id":1,"title":"写实验报告","done":false}]
```

**没有魔法。** 你能读、能背、能手写。

### 请求的第一行 = 三样东西

```
GET /todos HTTP/1.1
 │     │        └── 协议版本（现在几乎都是 1.1 或 2）
 │     └── 路径：我想要哪个资源
 └── 方法：我想干什么
```

### 请求的第二行开始 = Header（元数据）

```
Host: 127.0.0.1:8000        ← 我要找的是哪台机器上的哪个服务
User-Agent: Mozilla/5.0     ← 我是谁（什么浏览器/程序）
Accept: application/json    ← 我希望你用什么格式回答我
```

### 那个空行，是一条分隔线 ⚠️

**Header 结束、Body 开始，就是靠一个空行分界。**

这个细节能解释很多诡异问题：如果手工构造请求时忘了这个空行，服务器会把 body 当成又一个 header，然后一脸茫然。

### 响应的第一行 = 状态码

```
HTTP/1.1 200 OK
        └── 200 是给程序看的，OK 是给人看的
```

### 真正的内容在最后

```
[{"id":1,"title":"写实验报告","done":false}]
```

这行叫 **Body（响应体）**。前面那一坨都是"关于这封信的说明"，**只有这里才是信的内容**。

**关键认知**：`content-type: application/json` 这个 header 是在告诉对方——"我给你的这堆字节，请按 JSON 去解释"。

因为**底层只是字节流**，如果没有这个说明，对方根本不知道收到的是 JSON、HTML 还是图片。这跟 C 里 `void*` 指针必须配一个类型信息才能正确解释是同一个道理。

## 三、方法（动词）：语义约定，不是强制

| 方法 | 语义 | 对应待办的什么操作 | 幂等？ |
|---|---|---|---|
| `GET` | 读取 | 查看任务列表 | ✅ 是 |
| `POST` | 新建 | 新增一个任务 | ❌ 否 |
| `PUT` | 整体替换 | 改一个任务的**全部字段** | ✅ 是 |
| `PATCH` | 局部修改 | 只把 `done` 改成 true | ✅ 是 |
| `DELETE` | 删除 | 删掉一个任务 | ✅ 是 |

### 幂等是什么意思（这个概念其实已经会了）

数学上 `f(f(x)) = f(x)`。HTTP 里叫**幂等（idempotent）**：**同一个请求发一次和发十次，服务器的最终状态一样。**

- `DELETE /todos/1` 发十次 → 结果都是"1 号任务没了" ✅ 幂等
- `POST /todos`（新建"写作业"）发十次 → **会得到十个"写作业"** ❌ 不幂等

**这直接解释了一个肯定遇到过的现象**：

> 为什么刷新一个刚提交过表单的页面，浏览器会弹窗问"要重新提交吗？"

因为刷新 = 重发上一次的 `POST`，而 `POST` 不幂等，浏览器怕重复下单 / 重复发帖，所以拦一下。

### 一个重要提醒

**这些方法名是"约定"，不是"技术强制"。** 完全可以写一个 `GET /delete-everything` 来删数据，服务器也会照做。

那为什么必须守规矩？因为**全世界有无数中间设施靠这些约定工作**：

- 浏览器缓存（只缓存 GET）
- 搜索引擎爬虫（只爬 GET，绝不点 POST，否则会删数据）
- 公司防火墙、CDN、负载均衡器

破坏约定，它们就误解你。

> **这就是"RESTful"这个词的全部含义**：按大家的约定来设计接口。

## 四、URL 解剖

```
http://127.0.0.1:8000/todos/1?done=true
  │         │      │     │        └── 查询参数 Query String
  │         │      │     └── 路径 Path
  │         │      └── 端口
  │         └── 主机（这里是本机）
  └── 协议
```

### 两类参数，后面 FastAPI 会反复用到

**路径参数（Path Parameter）——"我要哪个东西"**

```
/todos/1     ← 1 号任务
/todos/2     ← 2 号任务
```

它是**资源标识**，回答"是哪一个"。所以在 FastAPI 里写成 `/todos/{id}`。

**查询参数（Query String）——"我要怎么筛"**

```
/todos?done=true            ← 只看已完成的
/todos?done=false&limit=10  ← 只看未完成的，且最多 10 条
```

它以 `?` 开始，多个用 `&` 连接，回答"怎么过滤/排序/分页"。

**怎么区分**：问自己"这个值是不是在指定'哪一个具体对象'？"是 → 路径参数；只是筛选条件 → 查询参数。

### 关于端口

端口号的作用可以直接类比**文件描述符**——同一台机器（同一个 IP）上要跑很多服务，端口就是区分"这封信该送给哪个程序"的编号。

`127.0.0.1` 是**回环地址**，专指"本机"。所以 `http://127.0.0.1:8000` 的意思是：**我自己这台机器上，监听 8000 端口的那个程序**。

**别人访问不了它**——这也是为什么阶段 7 要部署到服务器上，别人才能打开。

> `localhost` 和 `127.0.0.1` 基本是一回事。

## 五、状态码：先记大类，再记细节

**第一位数字就是大类**：

| 范围 | 含义 | 记法 |
|---|---|---|
| `1xx` | 信息，很少见 | 忽略 |
| `2xx` | **成功** | 好事 |
| `3xx` | **重定向**，去别处 | 你搬家了 |
| `4xx` | **客户端的错** | **你（请求方）错了** |
| `5xx` | **服务器的错** | **我（后端）崩了** |

### ⭐ 4xx 和 5xx 的区别，是调试时最重要的判断依据

- 看到 `4xx` → **问题在请求方**：路径写错了？数据格式不对？没登录？
- 看到 `5xx` → **问题在后端代码**：Python 抛异常了，去看后端终端里的报错

这一条能省下大量弯路。很多新手看到报错就乱改代码，其实压根是请求发错了。

### 最常遇到的几个

| 码 | 名字 | 什么时候出现 |
|---|---|---|
| `200` | OK | 成功 |
| `201` | Created | 成功创建了新资源（规范的 POST 应该返回它） |
| `400` | Bad Request | 传的数据不合法（业务层面） |
| `401` | Unauthorized | **没登录** |
| `403` | Forbidden | **登录了，但没权限** |
| `404` | Not Found | 路径不存在，或资源不存在 |
| `422` | Unprocessable Entity | **传的数据格式不对**（FastAPI 自动返回这个） |
| `500` | Internal Server Error | 后端代码抛异常了 |

> **401 vs 403**：401 = "你是谁？" 403 = "我知道你是谁，但你不许进。"

> **404 vs 422**：404 = "这个路径我没有"；422 = "路径对，但数据解析不了"。阶段 1 会亲眼看到——故意传错类型的数据，FastAPI 自动返回 422 加详细说明。

## 六、Header：为什么把"说明"和"内容"分开

Header 就是一堆 `键: 值` 的元数据。常见的有：

```
Content-Type: application/json      ← 内容的格式
Content-Length: 42                  ← 内容有多长（字节）
Authorization: Bearer xxxxx         ← 身份凭证
Accept: application/json            ← 我希望你回什么格式
```

**这个设计为什么好？** 因为它是**可扩展的**。以后需要新功能，加一个新的 header 名就行，**协议语法一个字都不用改**，老程序看到不认识的 header 直接忽略即可。

这跟"给结构体加字段但保持向后兼容"是同一个设计思路。对比一下：如果 HTTP 把格式写死成固定几个位置，那每加一个功能都要改协议版本，全世界都得跟着升级——网络效应的噩梦。

## 七、Body 与 JSON：为什么不直接传结构体

**Body 才是真正的内容**。约定上：

- `GET` 通常**没有** body（要的东西在 URL 里描述）
- `POST` / `PUT` / `PATCH` **有** body（要提交的数据）

**为什么用 JSON，而不是直接把 C 的结构体 `memcpy` 出去发过去？**

因为会有一堆问题：

| 问题 | 说明 |
|---|---|
| 字节序 | 你的机器小端，对方大端，数字全错 |
| 内存对齐 | 结构体里可能有 padding，对方不知道 |
| 指针 | 结构体里有指针就完蛋，传过去是个无意义的地址 |
| 类型尺寸 | `long` 在 Windows 是 4 字节，Linux 是 8 字节 |
| 语言差异 | 对方用的是 Python，根本没有"结构体"这东西 |

JSON 是**文本**，绕开了以上全部问题：任何语言、任何机器都能读写，而且**人眼可读**——这一点在调试时值千金。

**代价**：文本比二进制大、解析更慢。这是"通用性 vs 性能"的经典权衡。（性能敏感场景会用 Protobuf 这类二进制格式，那是后话。）

## 八、无状态（Stateless）：最重要的一个概念

**HTTP 的核心设计：服务器不记得你上次来过。**

每个请求都是**独立的、自包含的**。服务器处理完请求，关于你的记忆就清零了。

### 这和函数调用有本质区别

写函数时可以靠**全局变量**记住状态。但 HTTP 服务器不行——**下一个请求可能被发给另一台机器**。

### 为什么故意这么设计？

| 好处 | 说明 |
|---|---|
| **可扩展** | 用户太多了？直接加机器。请求发给哪台都行，因为哪台都不需要"记得"什么 |
| **简单** | 不用维护会话内存，不用考虑"用户断线了怎么清理" |
| **健壮** | 一台机器重启，不会丢失任何人的会话 |

如果服务器要记住每个用户的状态，那百万用户的会话内存就是灾难，而且用户连到哪台机器就绑死在那台上。**这是分布式系统的基本功。**

### 但代价是什么？

代价是：**"记住你是谁"这件事，必须靠额外机制实现。**

这就是 **Cookie / Session / Token** 存在的原因——它们是把状态"寄存在客户端"或"存在数据库里"的办法。这也是为什么后面做用户登录是整个项目里最烧脑的部分。

### ⭐ 这一条直接决定了项目架构

由此可以自己推出阶段 3 的存在理由：

> 阶段 1、2 里，任务列表存在 Python 的一个列表变量里。
> 但 HTTP 是无状态的，服务器随时可能重启、可能不止一台机器……
> **数据放在服务器内存里，就是不可靠的。**

所以要引入数据库——**数据库是唯一可靠的"记忆"**。

这不是"老师让我学数据库"，而是**无状态这个约束逼出来的必然结论**。

## 九、把所有概念串起来：一次请求的完整旅程

在浏览器敲 `http://127.0.0.1:8000/todos` 回车，然后：

```
1.  浏览器解析 URL，知道要找 127.0.0.1 的 8000 端口
2.  建立 TCP 连接（三次握手）         ← 连接层，HTTP 跑在它上面
3.  浏览器拼出那段纯文本请求，写进连接
4.  Uvicorn 收到字节，解析成"方法 GET、路径 /todos"
5.  Uvicorn 查 FastAPI 的路由表
6.  找到你写的那个函数，调用它
7.  你的 Python 代码跑起来，返回一个 dict
8.  FastAPI 把 dict 序列化成 JSON 文本
9.  Uvicorn 加上状态行和 header，写成响应文本发回去
10. 浏览器收到，按 content-type 解释成 JSON，渲染成页面
```

### ⭐ 现在能真正看懂 `@app.get("/todos")` 了

那一行干的事情，本质是：

> **往一张"路由表"里登记一条：当收到"方法=GET、路径=/todos"的请求时，调用下面这个函数。**

这个结构在操作系统课上见过——**中断向量表**：来了某个中断号，就跳去对应的处理函数。或者 C 里的**函数指针数组**：

```c
handler_t routes[][2] = { {"GET", "/todos", get_todos}, ... };
```

FastAPI 就是帮忙把这套"查表 + 调用 + 参数解析 + 序列化"的样板代码全包了。

> **这就是"框架"的本质**：它不替你写业务逻辑，它替你写那些每个 Web 项目都要写一百遍的胶水代码。

## 十、怎么亲眼看到这些（5 分钟，零成本）

**强烈建议做一次**，因为看过实物，上面所有文字才会落地：

1. 启动服务器：`uvicorn main:app --reload`
2. 浏览器按 **F12** 打开开发者工具 → 切到 **`Network`（网络）** 标签
3. 地址栏访问 `http://127.0.0.1:8000/docs`，然后点几下页面上的按钮
4. 在 Network 列表里点任意一条请求 → 看 **`Headers`** 和 **`Response`** 两个面板

会**亲眼看到第二节里那段纯文本**——请求方法、路径、状态码、header、JSON 响应，全都在。

> 这不是"写代码"，只是观察。但这 5 分钟的效果胜过读十篇教程。

## 十一、三个常见误解（提前排掉）

| 误解 | 事实 |
|---|---|
| "HTTP 是加密的" | ❌ **HTTP 是明文**。HTTPS 才加密，它是 HTTP 下面垫了一层 TLS。本地开发用 HTTP 完全没问题（因为不出本机） |
| "用 GET 还是 POST 取决于数据长度" | ⚠️ 民间流传的说法，不准确。**取决于语义**：读取用 GET，产生副作用用 POST。长度限制只是实现细节 |
| "服务器可以主动给我推消息" | ❌ HTTP 是**请求-响应**模式，**必须先有请求才有响应**，服务器不能主动开口。想要推送得用 WebSocket 或 SSE |

## 十二、一句话总结（速查表）

| 概念 | 一句话 |
|---|---|
| HTTP | 客户端和服务器之间**约定好的纯文本**对话格式 |
| 请求行 | 方法 + 路径 + 版本，回答"想干什么、对谁干" |
| 方法 | 语义约定，`GET` 读 / `POST` 增 / `PUT` 改 / `DELETE` 删 |
| 幂等 | 发一次和发十次效果一样；`POST` 不是，所以刷新会重复提交 |
| Header | 关于这封信的说明；**空行**是说明和正文的分界 |
| Body | 真正的正文内容，通常是 JSON |
| 状态码 | `2xx` 成功 / `4xx` 你的错 / `5xx` 我的错 |
| 无状态 | **服务器不记得你**；这是分布式扩展性的基石，也是必须用数据库的原因 |
| 路由表 | `@app.get("/todos")` = 往"路径+方法 → 函数"的映射表里登记一条 |
| JSON | 跨语言、可读的文本数据格式，避开了字节序/对齐/指针的坑 |

> **关于 CORS**：它不是 HTTP 协议的一部分，是**浏览器自己加的安全限制**。跨域报错时会发现"用 curl 能通、用浏览器就不行"——原因就在这里。阶段 5 再展开。
